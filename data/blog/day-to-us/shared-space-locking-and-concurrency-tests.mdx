# 코드의 조건문은 동시 요청에서도 규칙을 지킬까

Day To Us는 커플이 공간을 만들어 가계부와 일정을 공유하는 서비스다. 프로젝트를 더 잘 이해하려고 manware-ai-learning-toolkit을 사용해 AI와 문답을 진행했다. 처음에는 로그인 화면과 커스텀 훅의 역할을 확인했고, 이후 공간 생성과 참여 코드의 실패 상황을 따져봤다.

가장 오래 다룬 질문은 단순했다. 사용자에게 이미 공간이 있는지 검사하고, 공간 인원이 2명 이상인지 검사하는 코드가 있다. 그렇다면 동시에 요청이 들어와도 이 규칙은 지켜질까?

이 글은 코드 문답과 이후 구현·테스트를 정리한 학습 기록이다. 운영 DB 스키마와 격리 설정은 직접 조회하지 않았다. DB 설명은 PostgreSQL의 READ COMMITTED를 기준으로 하며, 검증은 별도 테스트 DB에서 수행했다. 문답에서 개선안을 논의한 뒤 AI와 함께 비관적 잠금과 동시성 테스트를 코드에 추가했다. 아웃박스는 별도 글에서 다루며 구현하지 않았다.

# 최초 화면과 최종 화면은 다르다

프런트엔드의 `src/features/space/hooks/useSpace.ts`는 다음 초깃값으로 시작한다.

```typescript
const [loading, setLoading] = useState(true)
const [isUnauthorized, setIsUnauthorized] = useState(false)
```

마운트 후 실행하는 `fetchSpace`는 토큰이 없으면 상태를 바꾸고 종료한다.

```typescript
const token = localStorage.getItem('accessToken')
if (!token) {
  setIsUnauthorized(true)
  setLoading(false)
  return
}
```

`src/App.tsx`의 `AppContent`는 인증 오류를 먼저 검사하고 로딩 여부를 검사한다. 따라서 최초 렌더링에서는 스플래시 화면을 반환하고 토큰이 없음을 확인한 뒤 다시 렌더링할 때 로그인 화면을 반환한다. 처음에는 최종 화면만 생각했지만 문답을 통해 초깃값과 effect 실행 시점을 구분했다.

이때 `loading: spaceLoading`은 객체에서 값을 꺼내며 이름을 바꾸는 문법이다. `hasSpace: !!space`는 공간 값을 boolean으로 바꾼다. `space`가 객체 또는 `null`인 현재 타입에서는 `space !== null`로 존재 여부를 더 직접 표현할 수도 있다. 가독성에 관한 대안으로 논의했으며 코드를 변경하지는 않았다.

# 생성 성공과 조회 실패를 같은 실패로 묶으면

같은 훅에서 공간을 생성하는 코드다. 배열 검증은 생략한 실제 코드 발췌다.

```typescript
const newSpace = await spaceApi.create({ name })
setSpace(newSpace)
const membersData = await spaceApi.getMembers()
// membersData의 배열 여부 검증
setMembers(membersData)
return newSpace
```

서버의 공간 생성이 성공해도 멤버 조회가 실패하면 이 함수의 catch로 들어간다. 공간 상태는 이미 설정했지만 호출자는 생성 실패를 받는다. `hasSpace`가 true가 되어 공간이 있는 화면으로 전환되는 한편 실패 토스트가 나오는 혼란이 생길 수 있다.

처음에는 생성한 공간을 취소하는 보상 트랜잭션을 떠올렸다. 하지만 뒤따른 읽기 실패가 앞선 생성까지 취소해야 하는 이유인지는 따로 판단해야 한다. 이미 다른 사용자가 참여한 공간을 삭제할 수도 있기 때문이다. 문답에서는 생성 성공을 유지하고 멤버 조회 실패를 별도로 표시해 재시도하는 접근을 논의했다. 이 부분은 후속 설계·구현이 남아 있다.

# 실제 스키마에서 UNIQUE가 보장하는 것

백엔드 엔티티를 확인하니 별도의 가입 테이블은 없다. `users`의 `shared_space_id`가 공간을 참조한다. 아래는 엔티티 매핑에서 확인한 핵심 구조다.

| 테이블         | 핵심 필드         | 역할                    |
| -------------- | ----------------- | ----------------------- |
| `users`        | `id`              | 사용자 PK               |
| `users`        | `email`           | NOT NULL, UNIQUE        |
| `users`        | `shared_space_id` | NULL을 허용하는 공간 FK |
| `shared_space` | `id`              | UUID PK                 |
| `shared_space` | `name`            | 공간 이름               |
| `shared_space` | `inviteCode`      | UNIQUE 초대 코드 속성   |

엔티티 경로는 백엔드의 `src/main/kotlin/com/dong/daytous/domain/user/User.kt`와 `domain/sharedspace/SharedSpace.kt`다. 초대 코드의 물리적 컬럼명은 명명 전략의 영향을 받으므로 엔티티 속성명으로 표기했다.

처음에는 사용자 식별 값의 UNIQUE 제약으로 중복 공간 생성도 막히지 않을까 생각했다. 하지만 사용자 행을 새로 만드는 요청이 아니다. 각 요청은 공간 행을 INSERT하고 기존 사용자의 외래키를 UPDATE한다. email은 바뀌지 않으므로 그 UNIQUE 제약과 충돌하지 않는다.

사용자 행에 외래키 하나만 저장한다는 구조는 최종 소속을 하나로 표현한다. 그러나 두 공간이 생성되거나 뒤 요청이 앞선 연결을 덮어쓰는 문제까지 해결하지는 않는다.

# 트랜잭션과 경쟁 조건을 구분하기

잠금을 추가하기 전 `SharedSpaceService.kt`의 공간 생성 로직을 발췌했다.

```kotlin
val user = userRepository.findByEmail(email)
    .orElseThrow { EntityNotFoundException("User not found") }

if (user.sharedSpace != null) {
    throw IllegalStateException("User already belongs to a shared space")
}

val newSpace = SharedSpace(name = name)
val savedSpace = sharedSpaceRepository.save(newSpace)
user.sharedSpace = savedSpace
```

두 트랜잭션이 모두 소속 공간이 없는 상태를 읽으면 다음 순서가 가능하다.

```text
A: 사용자 조회 → 소속 공간 없음
B: 사용자 조회 → 소속 공간 없음
A: 공간 A 생성 → 사용자 연결 → 커밋
B: 공간 B 생성 → 사용자 연결 → 커밋
```

둘 다 커밋되는 실행에서는 공간 두 개가 남고 사용자는 하나에만 연결될 수 있다. 변경 전 Repository에는 명시적 비관적 잠금이 없었다.

READ COMMITTED에서는 일반 조회마다 문장 시작 시점에 커밋된 데이터를 읽으며 자기 트랜잭션의 변경도 볼 수 있다. 같은 트랜잭션에서 다시 조회했을 때 다른 트랜잭션의 커밋으로 결과가 달라지는 것은 반복 불가능 읽기다. 그러나 위 경쟁 조건은 각 요청이 한 번만 읽어도 발생한다. 두 개념을 처음에는 섞어 생각했지만 실행 순서를 나눠보니 차이가 드러났다. [PostgreSQL 격리 수준 문서](https://www.postgresql.org/docs/18/transaction-iso.html)

`@Transactional`은 생성과 연결을 한 트랜잭션으로 묶는다. 이것만으로 두 요청의 검사와 변경이 순서대로 실행되지는 않는다.

# 어떤 규칙을 지킬지에 따라 잠글 행이 달라진다

`joinSharedSpace`에는 사용자 소속과 공간 정원이라는 두 검사가 있다. 잠금을 추가하기 전 실제 코드의 핵심 흐름이다.

```kotlin
val user = userRepository.findByEmail(email)
    .orElseThrow { EntityNotFoundException("User not found") }

if (user.sharedSpace != null) {
    throw IllegalStateException("User already belongs to a shared space")
}

val space = sharedSpaceRepository.findByInviteCode(inviteCode)
    .orElseThrow { EntityNotFoundException("Invalid invite code") }

if (space.users.size >= 2) {
    throw IllegalStateException("Shared space is full")
}

user.sharedSpace = space
```

잠금 대상은 보호할 규칙에 따라 달라진다.

| 상황                                | 하나만 잠글 때 남는 문제                                 | 논의한 잠금 대상 |
| ----------------------------------- | -------------------------------------------------------- | ---------------- |
| 같은 사용자가 공간을 두 번 생성     | 두 공간을 만들고 소속을 덮어쓸 수 있음                   | 사용자 행        |
| 다른 사용자 둘이 같은 공간에 참여   | 각 사용자 행은 다르므로 둘 다 정원 검사를 통과할 수 있음 | 공간 행          |
| 같은 사용자가 서로 다른 공간에 참여 | 각 공간 행은 다르므로 둘 다 소속 검사를 통과할 수 있음   | 사용자 행        |

참여 흐름의 개선안은 사용자 조회에서 잠금을 얻은 뒤 소속을 검사하고 공간 조회에서 잠금을 얻은 뒤 인원을 확인하는 것이다. 공간 인원은 잠금 이후에 읽어야 하며 이미 로딩된 JPA 컬렉션을 최신 DB 값이라고 단정해서도 안 된다. 같은 규칙에 영향을 주는 쓰기 경로들이 동일한 잠금 규약을 따라야 한다.

아래 SQL은 사용자 잠금을 설명하는 예시다. Repository에는 뒤에서 소개할 JPA 잠금 설정을 추가했다.

```sql
BEGIN;
SELECT * FROM users WHERE id = :user_id FOR UPDATE;
-- 소속 검사와 공간 생성·연결
COMMIT;
```

비관적 잠금은 UPDATE 코드가 끝났다고 해제되지 않고 트랜잭션 종료까지 유지된다. PostgreSQL READ COMMITTED에서 요청이 같은 사용자 행의 잠금을 기다렸다면 앞선 요청의 커밋 이후 갱신된 행을 확인할 수 있다. 앞선 요청이 롤백되면 연결 변경은 남지 않는다. [PostgreSQL 행 잠금 문서](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS)

# 실제 코드에 잠금 추가하기

문답을 마친 뒤 현재 코드에도 잠금을 추가하는 편이 좋겠다고 요청했다. 일반 조회를 모두 잠그지 않고 생성·참여에 사용할 조회 메서드를 따로 만들었다.

```kotlin
// UserRepository
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select u from User u where u.email = :email")
fun findByEmailForUpdate(email: String): Optional<User>

fun countBySharedSpaceId(spaceId: UUID): Long

// SharedSpaceRepository
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select s from SharedSpace s where s.inviteCode = :inviteCode")
fun findByInviteCodeForUpdate(inviteCode: String): Optional<SharedSpace>
```

생성은 사용자 행을 잠근 뒤 소속을 검사한다. 참여는 사용자 행을 먼저 잠그고 소속을 검사한 다음 공간 행을 잠근다. 공간 잠금 이후 `space.users.size` 대신 `countBySharedSpaceId`로 DB 인원을 조회한다. 이미 로딩된 컬렉션에 의존하지 않으려는 변경이다. 두 잠금은 기존 `@Transactional` 경계에서 커밋·롤백까지 유지한다.

```kotlin
// 변경한 joinSharedSpace의 핵심 발췌
val user = userRepository.findByEmailForUpdate(email)
    .orElseThrow { EntityNotFoundException("User not found") }

if (user.sharedSpace != null) {
    throw IllegalStateException("User already belongs to a shared space")
}

val space = sharedSpaceRepository.findByInviteCodeForUpdate(inviteCode)
    .orElseThrow { EntityNotFoundException("Invalid invite code") }

if (userRepository.countBySharedSpaceId(space.id!!) >= 2) {
    throw IllegalStateException("Shared space is full")
}

user.sharedSpace = space
```

실제 구현은 [SharedSpaceService.kt](https://github.com/dong5854/day-to-us-backend/blob/main/src/main/kotlin/com/dong/daytous/service/SharedSpaceService.kt)에서 확인할 수 있다.

# CountDownLatch로 출발을 맞춰도 실행 순서는 다를 수 있다

동시 참여 테스트의 최종 상태는 해당 공간에 연결된 사용자 수로 확인한다. 전체 사용자 수와는 구분해야 한다. 기존 멤버가 한 명이면 최종 인원은 2명이어야 한다. 참여 요청 하나는 성공하고 다른 하나는 정원 초과로 거절돼야 한다.

동시 실행을 만들기 위해 `CountDownLatch`를 설명받았다. 카운트가 0이 되면 기다리던 작업들이 진행하는 일회성 동기화 도구다. 두 작업의 준비와 출발 신호를 분리할 수 있다. 아래는 설명용 예시다. 현재 테스트에는 없는 코드이며 필요한 import와 예외 수집은 생략했다.

```kotlin
val ready = CountDownLatch(2)
val start = CountDownLatch(1)
val executor = Executors.newFixedThreadPool(2)

val tasks = listOf(userB, userC).map { user ->
    executor.submit {
        ready.countDown()
        check(start.await(5, TimeUnit.SECONDS))
        service.joinSharedSpace(inviteCode, user.email)
    }
}

check(ready.await(5, TimeUnit.SECONDS))
start.countDown()
// Future의 결과·예외를 제한 시간 내 수집하고 executor를 종료한다.
```

`ready`로 두 작업이 준비됐는지 기다린 뒤 메인 스레드가 출발을 허용할 때까지 `start`로 각 작업을 대기시킨다. `await(5, TimeUnit.SECONDS)`는 최대 5초 기다리고 카운트가 0이 됐으면 true, 시간 초과면 false를 반환한다. `check`는 false일 때 예외를 던져 출발 신호 없이 진행하는 것을 막는다. [Java CountDownLatch 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/CountDownLatch.html), [Kotlin check 문서](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin/check.html)

마지막에는 두 작업을 함께 출발시킨 테스트가 통과했을 때 경쟁 조건이 없다고 말할 수 있는지 물었다. 테스트 통과만으로는 그렇게 말할 수 없다. 출발을 허용한 뒤에도 한 트랜잭션이 끝나고 다른 트랜잭션이 진행될 수 있다.

잠금 없는 코드의 실패를 확실히 재현하려면 두 요청이 모두 인원을 1명으로 읽고 검사를 통과한 지점까지 도달한 뒤 연결을 진행하도록 제어해야 한다. 반대로 잠금이 적용된 코드에서는 첫 요청이 잠금을 가진 채 두 요청 모두 그 지점에 도달하기를 기다리면 테스트 자체가 막힐 수 있다. 실패 재현용 동기화와 잠금 동작 검증을 같은 방식으로 설계해서는 안 된다.

## 실제 테스트는 실패 재현과 잠금 검증을 나눈다

추가로 실제 테스트를 어떻게 구성해야 하는지 질문했다. 확인한 `src/test/kotlin/com/dong/daytous/service/SharedSpaceServiceTest.kt`는 Mockito로 Repository를 대체하는 단위 테스트다. 테스트 프로파일의 DB는 H2다. 단위 테스트만으로 PostgreSQL의 잠금·커밋·대기를 검증할 수는 없다.

첫 번째는 잠금 없는 구현의 경쟁 조건 재현이다. 실제 DB에서 각 요청이 인원을 1명으로 읽고 정원 검사를 통과한 직후까지 진행하도록 테스트용 제어 지점을 둔다. 두 요청이 모두 도달해야 사용자 연결을 진행시키면 두 요청의 판단이 겹쳤음을 보장할 수 있다. 아래는 그 제어의 의사 코드다. 현재 서비스에 이런 제어 지점은 없다.

```kotlin
// 각 요청에서 정원 검사 통과 직후 실행하는 테스트용 동기화
bothChecked.countDown()
check(bothChecked.await(5, TimeUnit.SECONDS))
// 두 요청 모두 검사를 통과했으므로 이후 연결 진행
```

두 번째는 잠금 적용 후의 통합 테스트다. 첫 요청이 공간 잠금을 획득한 뒤 커밋 직전에서 기다리도록 제어한다. 두 번째 요청을 실행하고 별도 관찰용 연결로 PostgreSQL의 잠금 대기와 차단 관계를 확인한다. 첫 요청을 커밋시킨 뒤 두 번째가 정원 초과로 거절되는지 확인한다. 단순히 Future가 잠깐 끝나지 않았다는 사실만으로는 DB 잠금 대기를 증명하지 못한다.

테스트 데이터는 작업 스레드에서 볼 수 있도록 미리 커밋하고 각 참여 호출은 Spring의 트랜잭션 프록시를 통해 독립된 트랜잭션에서 실행한다. 두 요청이 실제로 별도 DB 연결을 사용할 수 있도록 커넥션 풀도 확보한다. 검증은 작업 종료 후 새 조회로 수행하며 성공 하나·정원 초과 거절 하나·최종 인원 2명을 확인한다. 모든 대기에는 제한 시간을 두고 작업의 예외를 수집한다.

테스트용 제어는 테스트 범위의 계측으로 구성할 수 있고 필요하면 작은 관찰 지점을 둘 수 있다. 시간을 오래 기다리는 대신 실행이 특정 지점에 도달했음을 확인한다. 이 구성을 논의한 뒤 실제 테스트를 추가하고 실행했다. 적용한 방식은 다음 절에 정리한다.

# 출발 신호 대신 실제 잠금 대기를 확인한 테스트

`SharedSpaceConcurrencyTest`에는 세 경우를 추가했다. 같은 사용자의 중복 생성, 서로 다른 사용자의 정원 경쟁, 같은 사용자의 서로 다른 공간 참여다.

각 테스트는 첫 요청을 외부 `TransactionTemplate` 안에서 실행한 뒤 커밋 전에 기다리게 한다. 서비스의 트랜잭션은 이 트랜잭션에 참여하므로 서비스가 반환해도 잠금은 풀리지 않는다. 그 상태에서 두 번째 요청을 별도 스레드로 실행한다.

```kotlin
val firstResult = executor.submit {
    TransactionTemplate(transactionManager).executeWithoutResult {
        first()
        ready.countDown()
        check(commit.await(10, TimeUnit.SECONDS))
    }
}
check(ready.await(5, TimeUnit.SECONDS))
val secondResult = executor.submit<Throwable?> {
    runCatching { second() }.exceptionOrNull()
}
// 별도 연결에서 DB 잠금 대기를 확인한 뒤 commit.countDown() 실행
```

PostgreSQL에서는 관찰용 연결에서 다음 쿼리를 반복 조회한다. 단순히 Future가 끝나지 않았다는 사실 대신 실제 차단 관계가 생겼는지 확인하는 부분이다. 테스트마다 첫 작업과 둘째 작업만 실행하는 격리된 테스트 DB에서 사용했다.

```sql
select count(*)
from pg_stat_activity
where datname = current_database()
  and cardinality(pg_blocking_pids(pid)) > 0;
```

잠금 대기를 확인한 뒤 첫 요청의 커밋을 허용하고 두 번째 요청의 결과를 수집한다. 전체 테스트의 트랜잭션 자동 래핑은 끄고, 준비 데이터는 먼저 커밋한다. 각 대기와 Future 결과 수집에는 제한 시간이 있다. H2 실행에서는 해당 DB의 세션 정보를 조회하는 방식으로 같은 검증을 수행한다.

| 검증 상황                          | 첫 요청 | 두 번째 요청                   | 최종 DB 확인                             |
| ---------------------------------- | ------- | ------------------------------ | ---------------------------------------- |
| 같은 사용자 중복 생성              | 성공    | 이미 소속된 공간이 있다는 오류 | 공간 증가량 1개                          |
| 한 명이 있는 공간에 두 사용자 참여 | 성공    | 정원 초과 오류                 | 공간 인원 2명, 거절된 사용자는 미소속    |
| 같은 사용자 서로 다른 공간 참여    | 성공    | 이미 소속된 공간이 있다는 오류 | 첫 공간 소속 유지, 두 번째 공간 인원 0명 |

기존 H2 환경의 전체 백엔드 테스트 172개가 통과했다. 운영 설정과 같은 주요 버전인 PostgreSQL 16을 Docker로 따로 실행해 위 동시성 테스트 3개도 통과했다. SQL 로그와 DB 잠금 대기를 확인했으며 운영 DB에는 접속하지 않았다. 테스트용 컨테이너는 검증 후 제거했다.

실제 테스트는 [SharedSpaceConcurrencyTest.kt](https://github.com/dong5854/day-to-us-backend/blob/main/src/test/kotlin/com/dong/daytous/service/SharedSpaceConcurrencyTest.kt)에 있다. 잠금 없는 버전의 정원 초과를 강제로 재현하는 별도 테스트는 아직 추가하지 않았다.

# 다음에 확인할 것

같은 사용자와 같은 공간을 보호하는 잠금은 역할이 다르다. 이 구분을 문답으로 확인하고 실제 코드에 적용했다. 함께 출발시키는 것만으로 경쟁 조건을 검증할 수 없다는 점도 테스트의 잠금 대기 관찰로 연결했다.

다음에는 잠금 없는 버전의 실패 재현과 현재 잠금 검증을 비교해보고 싶다. 이번 통합 테스트는 세 경쟁 상황에서 실제 대기가 발생하고 요청 결과와 최종 DB 상태가 맞는지 확인한 범위다.
