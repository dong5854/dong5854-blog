# 공간 참여 이후의 작업을 가정해보기

Day To Us의 공간 참여 코드를 AI와 읽으며 트랜잭션과 비관적 잠금을 학습했다. 이후 공간 참여가 끝나면 이메일을 보낸다는 가정으로 문답을 이어갔다. 이 글은 그 과정에서 이해한 아웃박스와 중복 처리 기록이다.

현재 프로젝트에 이 이메일 API 호출, 메시지 큐, 아웃박스를 구현한 것은 아니다. 실제 코드의 공간 잠금과 동시성 테스트는 별도 글에 정리했고, 여기서는 DB와 외부 작업 사이의 실패 상황을 다룬다.

---

# 외부 작업으로 확장하며 아웃박스를 이해하기

이후에는 공간 참여 후 이메일을 보내는 가정으로 확장했다. 실제 참여 코드에는 초대 이메일 API 호출이나 아웃박스가 없다.

외부 API가 5초 걸린다면 그 호출을 DB 트랜잭션 안에 두는 동안 잠금과 커넥션도 오래 점유한다. 트랜잭션이 끝난 뒤 큐에 작업을 보내 재시도하는 방식을 제안했지만 DB 커밋 직후 큐에 보내기 전에 프로세스가 종료되는 틈이 남았다.

아웃박스는 업무 변경과 발송할 이벤트 기록을 같은 DB 트랜잭션에 저장한다. 별도 릴레이가 커밋된 기록을 읽어 큐에 전달한다. 업무 변경은 커밋됐는데 발행할 기록은 없는 상황을 막는 접근이다. [AWS 아웃박스 패턴 설명](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

```text
업무 트랜잭션: 사용자 연결 + outbox 이벤트 저장 → 커밋
릴레이: 미발행 이벤트 조회 → 큐 발행 → 발행 완료 기록
소비자: 메시지 수신 → 이메일 발송 → 처리 확인
```

릴레이는 반드시 별도 프로세스일 필요는 없다. 앱 내부 스케줄러로 시작할 수도 있다. 다만 여러 인스턴스에서 같은 테이블을 조회한다면 이벤트 선점이 필요하다. 폴링 외에 CDC를 쓰는 선택도 있으나 이번에는 구현을 다루지 않았다.

PostgreSQL에서는 설명용 쿼리처럼 잠긴 행을 건너뛰며 작업을 나눌 수 있다. 잠금과 선점은 트랜잭션 경계 안에서 설계해야 한다.

```sql
SELECT *
FROM outbox_events
WHERE status = 'PENDING'
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;
```

`SKIP LOCKED`는 다른 작업자가 잠근 행을 기다리지 않고 건너뛴다. 일반적인 조회의 완전한 일관성 대신 큐처럼 행을 나눠 처리하는 용도에 적합하다. [PostgreSQL SELECT 문서](https://www.postgresql.org/docs/18/sql-select.html)

선점 잠금만으로 중복 발행까지 막히지는 않는다. 큐 발행은 성공했는데 발행 완료 기록이 롤백되면 같은 이벤트가 다시 조회된다. 재발행 시에는 새 ID가 아니라 기존 `event_id`를 유지해야 소비자가 같은 이벤트로 식별할 수 있다.

# 처리 기록과 외부 발송 사이에도 틈이 있다

이벤트 ID를 기록하면 중복을 판별할 수 있다고 답했다. 다만 일반 로그 출력보다 영속적인 처리 기록이 필요하고 기록 시점도 중요했다.

| 처리 순서와 장애                            | 결과                  |
| ------------------------------------------- | --------------------- |
| 완료 기록 → 이메일 실패 → 재시도에서 건너뜀 | 이메일 누락           |
| 이메일 성공 → 완료 기록 전 종료 → 재시도    | 이메일 중복 발송 가능 |

같은 DB 안의 업무 변경과 처리 기록은 트랜잭션으로 묶을 수 있지만 외부 이메일 발송은 그 DB 트랜잭션에 함께 커밋되지 않는다. 이메일 API가 멱등성 키를 지원하고 계약상 중복 처리를 막아준다면 같은 이벤트의 재시도에 동일한 `event_id`를 전달하는 방법이 있다.

API의 키 보관 기간과 적용 범위를 확인해야 한다. 아웃박스만 도입했다고 외부 효과가 정확히 한 번 발생한다고 단정할 수는 없다. 이번 문답에서는 이벤트 ID 유지와 누락·중복의 실패 순서를 설명했고 구체적인 이메일 제공자 계약은 확인하지 않았다.

---

# 이번 문답에서 구분한 것

DB 커밋 후 큐에 보내는 방식에는 이벤트가 유실되는 틈이 남는다. 아웃박스로 발행할 기록을 업무 변경과 함께 저장해도 릴레이의 중복 발행은 가능하다. 재발행에는 같은 `event_id`를 유지하고 소비자와 외부 API의 멱등성을 함께 고려해야 한다.

문답에서는 처리 완료를 먼저 기록하면 발송 누락이 생기고, 발송 후 기록하면 중복이 생길 수 있다는 순서를 설명했다. 구체적인 이메일 제공자 계약과 아웃박스 구현은 아직 확인하지 않았다.

> [!NOTE]
> 실제 기능을 구현하게 되면 이메일 API의 멱등성 키 보관 기간과 적용 범위, 릴레이의 선점·재시도 방식을 추가한다.
