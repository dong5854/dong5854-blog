## 1. ArgoCD 계정의 두 가지 capability

ArgoCD의 로컬 계정은 두 가지 능력(capability)을 따로 켤 수 있습니다.

| capability | 무엇을 할 수 있나 | 누구에게 |
|---|---|---|
| `login` | UI/CLI에 username+password로 로그인 | 사람 |
| `apiKey` | JWT 토큰을 발급받아 비대화형 API 호출 | CI/CD 봇 |

`login`만 가진 계정은 토큰을 발급받을 수 없습니다. 반대로 `apiKey`만 가진 계정은 패스워드로 UI 로그인이 불가능하고 admin이 대신 토큰을 발급해 줘야 합니다. 둘을 동시에 켤 수도 있지만 그러면 한 계정이 사람용과 자동화용 권한을 다 갖게 되어 보안 경계가 흐려집니다.

> [!NOTE]
> 별도 capability를 명시하지 않은 `admin`은 ArgoCD 내부적으로 둘 다 켜져 있는 특수 계정입니다. 새 계정에는 필요한 것만 좁게 부여하는 편이 깔끔합니다.

이번에는 **사람용 admin 계정 하나**와 **CI/CD 전용 봇 계정 하나**를 분리해서 만들었습니다.

- `dong5854` (login) - 사람이 UI로 들어와서 클러스터 상태를 보고 필요시 직접 sync 트리거
- `cicd-bot` (apiKey) - 향후 자동화에서 즉시 sync를 호출하고 싶을 때를 대비. 이번 글의 GitOps 파이프라인에서는 사용하지 않음

분리하면 세 가지 이점이 명확해집니다.

1. **감사 로그 분리** - 누가 사람 sync고 누가 자동화 sync인지 한눈에 보입니다.
2. **권한 좁히기** - 봇에게는 admin 권한이 필요 없고 특정 프로젝트 sync 권한만 줘도 충분합니다.
3. **토큰 회수 단위** - 봇 토큰이 유출되면 봇 계정만 비활성화하면 끝납니다. 사람 계정은 그대로 두면 됩니다.

## 2. Helm values로 계정과 RBAC 선언적으로 관리

ArgoCD가 차트로 설치되어 있다면 계정과 RBAC은 `argocd-cm`과 `argocd-rbac-cm` 두 ConfigMap에 들어갑니다. 처음에는 이 두 ConfigMap을 Kustomize patch로 관리해 볼까 했는데 Helm이 이미 두 리소스를 소유한 상태에서 Kustomize가 같은 이름으로 ConfigMap을 또 만들면 충돌합니다.

> [!WARNING]
> Helm으로 설치한 차트의 ConfigMap을 Kustomize patch로 덮어쓰지 마세요. 다음 `helm upgrade` 때 helm 쪽이 자기 소유로 인식한 필드를 다시 reconcile 하면서 patch한 값을 날립니다. 차트가 values 키를 제공한다면 그쪽으로 가는 게 정답입니다.

다행히 `argo-cd` 차트는 `configs.cm`, `configs.rbac`, `configs.params` 세 키를 통해 ConfigMap 내용을 그대로 노출합니다. 이걸 활용해서 다음 `values.yaml`을 매니페스트 레포에 두고 `helm upgrade`로만 반영하기로 했습니다.

```yaml:argocd/values.yaml
global:
  domain: argocd.movingzero.org

configs:
  cm:
    url: https://argocd.movingzero.org
    accounts.dong5854: login
    accounts.cicd-bot: apiKey

  rbac:
    policy.default: ""
    scopes: "[groups]"

    policy.admins.csv: |
      g, dong5854, role:admin

    policy.cicd.csv: |
      p, role:cicd, applications, get,  default/*, allow
      p, role:cicd, applications, sync, default/*, allow
      g, cicd-bot, role:cicd

  params:
    server.insecure: true
```

### 2.1 url과 server.insecure

`url`은 ArgoCD가 만드는 OIDC redirect와 webhook 콜백 등에 쓰이는 외부 주소입니다. 차트 디폴트가 `https://argocd.example.com`이라 외부 접속이 본격화되면 이 값을 반드시 자기 도메인으로 바꿔 줘야 합니다.

`server.insecure: true`는 TLS 종단을 Gateway에서 하기 때문에 ArgoCD 컨테이너 안에서는 HTTP로 동작하라는 의미입니다. 지난 글에서 만든 NGINX Gateway Fabric이 와일드카드 인증서로 HTTPS를 받고 평문 HTTP로 백엔드에 흘려 보내는 구조와 맞물립니다.

### 2.2 RBAC: 정책을 역할별로 쪼개기

ArgoCD RBAC은 내부적으로 Casbin을 쓰고 정책 포맷은 **CSV만** 지원합니다. YAML이나 JSON으로 쓸 수 있으면 좋겠지만 Casbin 라이브러리 자체의 제약입니다.

그래도 ArgoCD는 `policy.<이름>.csv` 형태의 추가 키를 모두 머지해 주기 때문에 정책을 역할별로 쪼개 둘 수 있습니다. 위 values를 보면 `policy.admins.csv`와 `policy.cicd.csv`로 사람 권한과 봇 권한을 시각적으로 분리했습니다.

```
p, role:cicd, applications, get,  default/*, allow
p, role:cicd, applications, sync, default/*, allow
g, cicd-bot, role:cicd
```

이 세 줄을 풀어 쓰면 다음과 같습니다.

- `p`로 시작하는 두 줄은 정책(policy) - `role:cicd`는 `default` 프로젝트의 모든 Application에 대해 `get`과 `sync`만 가능
- `g`로 시작하는 줄은 그룹(group) 매핑 - `cicd-bot`이라는 사용자를 `role:cicd`에 묶음

봇에게 `applications, create`나 `clusters, update` 같은 권한을 주지 않았기 때문에 토큰이 유출돼도 새로운 앱을 등록하거나 클러스터 설정을 건드릴 수는 없습니다.

### 2.3 적용

values.yaml을 만들었다면 helm upgrade 한 번이면 끝입니다.

```bash
helm upgrade argocd argo/argo-cd \
  -n argocd \
  --version 9.3.7 \
  -f argocd/values.yaml
```

`--version`을 명시한 이유는 의도치 않은 차트 업그레이드를 막기 위해서입니다. 차트 메이저 버전이 바뀌면 values 스키마도 바뀔 수 있어서 손에 익은 버전에 고정해 두는 편이 안전합니다.

## 3. ArgoCD CLI 설치와 admin 비밀번호 트러블슈팅

values 반영까지 끝나면 그 다음은 CLI로 계정 비밀번호를 설정하고 토큰을 발급하는 작업입니다. CLI는 서버 버전과 똑같은 바이너리로 깔아 두는 편이 안전합니다.

```bash
curl -sSL -o /tmp/argocd \
  https://github.com/argoproj/argo-cd/releases/download/v3.2.6/argocd-linux-amd64
sudo install -m 555 /tmp/argocd /usr/local/bin/argocd
rm /tmp/argocd
argocd version --client
```

설치 후 admin으로 로그인합니다.

```bash
argocd login argocd.movingzero.org --grpc-web --username admin
```

> [!TIP]
> Gateway에서 TLS 종단하고 백엔드에는 HTTP/2 gRPC 대신 HTTP/1.1로 들어오는 환경이라면 `--grpc-web` 옵션이 필요합니다. 빼면 `transport is closing` 같은 RPC 에러가 납니다.

### 3.1 "Invalid username or password"

처음 로그인할 때 가장 흔히 만나는 함정입니다. `argocd-initial-admin-secret`에 들어 있는 초기 admin 비밀번호가 **stale인 경우가 많습니다**.

```bash
# 초기 비밀번호 조회
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath='{.data.password}' | base64 -d; echo

# 현재 admin 비밀번호의 마지막 변경 시각
kubectl -n argocd get secret argocd-secret \
  -o jsonpath='{.data.admin\.passwordMtime}' | base64 -d; echo
```

`passwordMtime`이 설치 시각과 다르다면 누군가(혹은 과거의 본인이) 한 번 admin 비밀번호를 바꿨다는 뜻입니다. 그러면 `argocd-initial-admin-secret`의 값은 더 이상 유효하지 않습니다.

해결은 두 가지입니다.

1. 변경한 비밀번호가 기억나면 그 값으로 로그인
2. 기억나지 않으면 ArgoCD가 제공하는 표준 리셋 절차를 따라 새 초기 비밀번호 발급

```bash
kubectl -n argocd patch secret argocd-secret \
  -p '{"data":{"admin.password": null, "admin.passwordMtime": null}}'

kubectl -n argocd rollout restart deploy argocd-server
kubectl -n argocd rollout status deploy argocd-server

kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath='{.data.password}' | base64 -d; echo
```

`admin.password`와 `admin.passwordMtime`를 지운 뒤 서버를 재시작하면 ArgoCD가 새 비밀번호를 만들어 `argocd-initial-admin-secret`에 다시 채워 줍니다.

## 4. 사용자 비밀번호 설정과 CI/CD 봇 토큰 발급

admin 로그인까지 됐다면 계정 두 개에 각각 필요한 작업을 합니다.

### 4.1 dong5854 비밀번호 설정

ArgoCD는 보안상 **다른 사용자의 비밀번호를 UI에서 admin이 직접 변경할 수 없게 막아 두었습니다**. 본인만 자기 비밀번호를 바꿀 수 있는 구조여서 초기 비밀번호 설정은 CLI나 API로 한 번 admin이 대신 해 줘야 합니다.

```bash
argocd account update-password --account dong5854
# *** Enter password of currently logged in user (admin): ...
# *** Enter new password for user dong5854: ...
```

이후 dong5854 본인은 UI에서 우측 상단 프로필 → User Info → Update Password로 바꿀 수 있습니다.

### 4.2 cicd-bot 토큰 발급

```bash
argocd account generate-token --account cicd-bot
# eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

이 JWT는 **한 번만 출력**됩니다. 잃어버리면 새로 발급받아야 하므로 즉시 안전한 곳에 저장합니다.

> [!WARNING]
> 토큰을 평문 파일로 홈 디렉토리에 던져 두지 마세요. 저장은 GitHub Actions의 secret(repo/org/environment) 또는 1Password Bitwarden 같은 비밀번호 관리자가 적합합니다. 만에 하나 평문 파일을 만들었다면 secret 등록 직후 `shred -u` 같은 명령으로 안전하게 지웁니다.

이번 글의 파이프라인 자체에서는 이 토큰을 쓰지 않습니다. 그래도 봇 계정을 미리 만들어 두면 나중에 별도 자동화(예: Slack 슬래시 커맨드로 sync 트리거)가 필요해질 때 토큰만 새로 뽑아 쓰면 되니 권한 좁히기는 미리 해 둘 가치가 있습니다.

## 5. CI는 GitHub Actions CD는 ArgoCD

여기서부터 큰 그림을 한 번 정리하고 갑니다. ArgoCD를 "CI/CD 도구"라고 묶어 부르는 자료가 많지만 ArgoCD는 정확히는 **CD 전용**이고 그것도 **GitOps 방식의 CD**입니다.

| 단계 | 약자 | 역할 | 도구 |
|---|---|---|---|
| CI | Continuous Integration | 빌드 테스트 이미지 생성 푸시 | **GitHub Actions** Jenkins 등 |
| CD | Continuous Deployment | 만들어진 이미지를 클러스터에 배포 | **ArgoCD** Flux 등 |

day-to-us 백엔드 코드를 푸시하면 일어나야 하는 일을 두 단계로 나누면 다음과 같습니다.

1. **CI 영역** - GitHub Actions가 코드를 빌드해서 Docker 이미지를 만들고 레지스트리에 푸시
2. **CD 영역** - ArgoCD가 클러스터의 desired state(매니페스트)와 actual state를 동기화

여기서 갈리는 질문은 "**CI가 만든 새 이미지를 CD가 어떻게 알아채게 할 것인가**"입니다. ArgoCD는 git을 watch하니까 결국 어딘가의 git에 새 이미지 태그가 commit되어야 합니다. 그 commit을 누가 만들고 어디에 만들지가 다음 절의 주제입니다.

## 6. 매니페스트를 어디에 둘 것인가

GitOps 글들을 보면 거의 항상 **매니페스트 전용 repo**를 별도로 두라고 권합니다.

```
[app-source repo]      ← 코드만
[gitops-manifests repo] ← 매니페스트만, 클러스터 전체 desired state
```

이 구조의 장점은 명확합니다.

- 클러스터 전체 상태가 한 repo에 모이므로 "지금 우리 클러스터에 뭐가 떠 있는지" 파악이 빠릅니다.
- 코드 변경과 배포 변경이 다른 PR로 분리됩니다.
- 여러 앱이 공유하는 클러스터 인프라(Gateway Cluster Issuer 등)와 자연스럽게 동거합니다.

그래서 처음에는 저도 `homeserver-kubernetes`라는 매니페스트 전용 repo에 day-to-us 매니페스트를 같이 두었습니다. 그런데 **이 구조에는 한 가지 부담스러운 비용**이 따라옵니다.

### 6.1 분리 repo의 비용: PAT

GitHub Actions 워크플로우는 자기 repo에 대해 자동 발급되는 `GITHUB_TOKEN`을 가집니다. 자기 repo에 push도 GHCR에 이미지 push도 다 이 토큰 하나면 됩니다. 그런데 **다른 repo에 push하려면 이 토큰이 안 됩니다**. 별도 PAT(Personal Access Token)를 만들어 두 repo의 secret으로 등록해 두어야 합니다. 토큰 발급 만료 갱신 폭발 반경 같은 운영 부담이 따라오는 셈입니다.

홈서버 1인 운영에서 이 비용이 정당화될 만큼 분리 repo의 장점이 큰가? 결론은 "그렇지 않다"였습니다. 매니페스트를 코드 옆에 두는 **모노레포 GitOps 패턴**으로 갔습니다.

### 6.2 모노레포 GitOps

```
[day-to-us-backend repo]
├── src/                       ← 코드
├── Dockerfile
└── k8s/                       ← 매니페스트 ← ArgoCD가 여기를 watch
    ├── base/
    └── overlays/prod/

[day-to-us-frontend repo]
├── src/
├── Dockerfile
└── k8s/
    └── ...

[homeserver-kubernetes repo]   ← 클러스터 인프라만 남김
├── argocd/                    ← ArgoCD Helm values + Application 매니페스트
├── calico/
├── cluster-issuer.yaml
├── gateway.yaml
└── ...
```

핵심은 **세 가지**입니다.

1. ArgoCD는 git repo의 **path 단위로 watch**할 수 있습니다. 코드와 매니페스트가 같은 repo에 있어도 `path: k8s/overlays/prod`만 보게 하면 됩니다.
2. CI가 자기 repo의 매니페스트를 수정하고 commit/push 하면 `GITHUB_TOKEN`만으로 충분합니다. **PAT 불필요**.
3. **GitHub에는 빌트인 안전장치**가 있어서 `GITHUB_TOKEN`이 만든 commit은 자기 워크플로우를 재트리거하지 않습니다. 무한 루프 걱정 없음.

클러스터 인프라(`argocd`, `gateway`, `calico` 등)는 어느 앱에도 안 묶이는 컴포넌트라 그대로 `homeserver-kubernetes`에 남깁니다. **앱과 인프라가 정확히 owner가 다른 두 종류의 리소스**이므로 repo가 다른 게 오히려 자연스럽습니다.

## 7. 매니페스트 GHCR 마이그레이션과 Kustomize seam

모노레포에서 ArgoCD GitOps가 동작하려면 두 가지 준비가 필요합니다.

1. 이미지 레지스트리를 GitHub Actions에서 자연스럽게 푸시할 수 있는 곳(**GHCR**)으로 옮기기
2. 매니페스트 안에 **CI가 update할 수 있는 깔끔한 seam**(이미지 태그를 고치는 한 자리) 만들기

### 7.1 GHCR vs Docker Hub

| | GHCR (`ghcr.io`) | Docker Hub |
|---|---|---|
| 가입 | GitHub 계정으로 자동 | 별도 가입 필요 |
| GitHub Actions 인증 | 내장 `GITHUB_TOKEN` | 별도 PAT/Secret 필요 |
| 무료 private 이미지 | 개인 계정 제한 거의 없음 | 1개로 제한 |
| 익명 pull rate limit | 거의 없음 | 6시간당 100건 |
| 통합도 | GitHub repo와 같은 계정 아래 묶임 | 별개 |

GitHub Actions로 자동화한다면 **GHCR을 쓰는 게 거의 모든 면에서 편합니다**.

### 7.2 base 매니페스트의 이미지 주소 교체

기존에 `dong5854/day-to-us-backend:latest` (Docker Hub 디폴트)로 적어 두었던 부분을 `ghcr.io/dong5854/day-to-us-backend:latest`로 교체합니다.

```yaml:k8s/base/deployment.yaml
spec:
  containers:
  - name: backend
    image: ghcr.io/dong5854/day-to-us-backend:latest
```

### 7.3 overlay에서 image 태그 분리

GitOps에서 가장 흔한 안티패턴이 **base 매니페스트의 이미지 태그를 매번 CI가 직접 수정하는 것**입니다. base 파일은 환경이 다르면 다른 값을 갖고 싶어지는데 거기에 환경별로 다른 태그까지 박아 두면 base의 본래 의미(공유 가능한 베이스 정의)가 무너집니다.

Kustomize에는 이걸 위한 **`images:` 필드**가 있습니다. overlay 단계에서 base 이미지의 이름을 매핑해서 태그(또는 다이제스트)만 교체할 수 있게 해 줍니다.

```yaml:k8s/overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - ../../base

images:
  - name: ghcr.io/dong5854/day-to-us-backend
    newTag: latest
```

이제 CI가 update할 자리는 단 한 줄, `newTag: latest`입니다.

## 8. ArgoCD Application 등록과 auto-sync

ArgoCD가 day-to-us 앱을 관리하게 하려면 클러스터에 `Application` CR을 만들어 줘야 합니다. 이 매니페스트는 인프라 성격이라 `homeserver-kubernetes` repo의 ArgoCD base에 둡니다.

```yaml:argocd/base/application-day-to-us-backend.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: day-to-us-backend
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: default
  source:
    repoURL: https://github.com/dong5854/day-to-us-backend.git
    targetRevision: main
    path: k8s/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: day-to-us
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
      - ServerSideApply=true
```

각 필드의 의미를 한 번 짚고 갑니다.

- `source.repoURL` - **코드 repo 자체**. 모노레포 패턴이라 매니페스트도 여기 있음
- `source.path` - 그 repo 안에서 어떤 디렉토리만 sync 대상으로 삼을지. 여기선 `k8s/overlays/prod`
- `destination` - 어느 클러스터의 어느 네임스페이스에 배포할지. `kubernetes.default.svc`는 ArgoCD가 돌고 있는 자기 자신 클러스터를 의미
- `syncPolicy.automated.prune` - git에서 사라진 리소스를 클러스터에서도 제거
- `syncPolicy.automated.selfHeal` - 누군가 클러스터에서 직접 리소스를 수정해도 매니페스트 상태로 되돌림
- `finalizers` - Application을 지울 때 desired resources도 함께 정리

> [!TIP]
> `ServerSideApply=true`는 큰 CRD나 webhook 어노테이션이 붙은 리소스를 다룰 때 client-side apply의 한계를 회피해 줍니다. 단일 노드 홈서버에선 안 켜도 큰 문제는 없지만 켜 두면 safer합니다.

`day-to-us-frontend`도 똑같은 구조의 Application 매니페스트를 추가하고 `argocd/base/kustomization.yaml`의 `resources:`에 두 파일을 더해 줍니다.

```yaml:argocd/base/kustomization.yaml
resources:
  - argocd-httproute.yaml
  - application-day-to-us-backend.yaml
  - application-day-to-us-frontend.yaml
```

처음 한 번은 손으로 적용해 등록합니다.

```bash
kubectl apply -k argocd/overlays/prod
```

이후로는 이 Application 매니페스트 자체도 git에 있기 때문에 추가 변경은 commit 한 번으로 ArgoCD가 알아챕니다.

## 9. GitHub Actions 워크플로우

모노레포 패턴에서는 CI가 **자기 repo의 매니페스트를 직접 고치고** 같은 repo에 commit하면 끝입니다. 워크플로우 한 잡 안에서 빌드 푸시 매니페스트 갱신 commit-back을 다 처리합니다.

```yaml:.github/workflows/docker-publish.yml
name: Build and Deploy

on:
  push:
    branches: [main]
    paths-ignore:
      - 'k8s/overlays/**/kustomization.yaml'
  workflow_dispatch:

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: dong5854/day-to-us-backend
  MANIFEST_FILE: k8s/overlays/prod/kustomization.yaml

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: write
      packages: write
    steps:
      - uses: actions/checkout@v4

      - id: meta
        run: echo "tag=${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"

      - name: Set up JDK 21
        uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: temurin

      - name: Build jar
        uses: gradle/gradle-build-action@v3
        with:
          arguments: clean build -x test

      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: |
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ steps.meta.outputs.tag }}
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Update image tag in overlay
        env:
          TAG: ${{ steps.meta.outputs.tag }}
        run: |
          yq -i '.images[0].newTag = strenv(TAG)' "$MANIFEST_FILE"

      - name: Commit and push manifest
        env:
          TAG: ${{ steps.meta.outputs.tag }}
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add "$MANIFEST_FILE"
          git diff --staged --quiet && exit 0
          git commit -m "ci: 이미지 태그를 $TAG 로 갱신"
          git push
```

### 9.1 디테일 몇 가지

**`paths-ignore`로 자기 commit 제외** - 워크플로우가 자기 자신을 push해 무한 루프를 만드는 걸 막는 1차 방어선입니다. 사실 `GITHUB_TOKEN`으로 만든 commit은 GitHub이 알아서 워크플로우 재트리거를 막아 주지만 그래도 명시적으로 적어 두면 의도가 분명합니다.

**`permissions: contents: write`** - 워크플로우가 자기 repo에 commit/push할 권한이 필요합니다. 디폴트는 read-only라서 명시적으로 켜 줘야 합니다.

**`actions/checkout@v4` 기본 사용** - 분리 repo였다면 `repository:`, `token:` 옵션을 줘야 했지만 자기 repo면 옵션 없이도 자동으로 `GITHUB_TOKEN`을 credential helper로 설정해 줍니다. 이후의 `git push`는 그냥 됩니다.

**short-SHA 태깅** - `${GITHUB_SHA::7}`로 7자리 short hash를 태그로 씁니다. 같은 코드는 같은 태그를 받아 멱등하고 다른 코드는 항상 다른 태그를 받습니다. `:latest`도 같이 푸시해 두면 디버깅용으로 편합니다.

**`GITHUB_TOKEN`으로 GHCR 인증** - GitHub Actions가 자동 발급하는 토큰입니다. workflow의 `permissions: packages: write`만 켜 주면 GHCR에 push할 수 있습니다. 별도 secret 등록이 필요 없습니다.

**`yq`로 in-place 수정** - `yq -i '.images[0].newTag = strenv(TAG)' "$MANIFEST_FILE"` 한 줄로 overlay의 태그 필드만 깔끔하게 교체됩니다. `sed`로도 가능하지만 파일 구조가 조금 바뀌면 매번 깨지기 쉬워 yq가 안전합니다.

**`git diff --staged --quiet && exit 0`** - 매니페스트가 실제로 바뀌지 않은 경우 빈 커밋을 만들지 않고 그냥 종료합니다.

프론트엔드 워크플로우도 거의 같습니다. JDK/Gradle 단계 대신 Vite + nginx multi-stage Dockerfile을 그대로 빌드하고 `VITE_API_BASE_URL` 같은 build-arg를 environment variable에서 받아 넣어 줍니다.

## 10. 남은 일과 TODO

여기까지가 이번 작업의 핵심이지만 실제 production에 돌리기 전에 몇 가지 작업이 남아 있습니다. 다음 글에서 이어서 정리할 예정입니다.

- [ ] **dev → main 머지** - 백엔드/프론트엔드 두 repo 모두 dev에 누적된 작업이 main에 안 올라가 있어 첫 CI 트리거가 안 됨. 기존 PR 기반 워크플로우대로 GitHub UI 또는 `gh pr create`로 PR 만들고 머지
- [ ] **GHCR 이미지 public 전환** - 첫 푸시 후 visibility 변경. 안 하면 cluster pull 실패
- [ ] **`kubectl apply -k argocd/overlays/prod`** - Application CR 등록. 이 한 번만 손으로
- [ ] **기존 Docker Hub secret 정리** - 양쪽 repo의 `DOCKER_USERNAME` `DOCKER_PASSWORD`는 더 이상 쓰지 않음
- [ ] **regcred 정리** - cluster의 `imagePullSecrets: regcred`는 Docker Hub용. public GHCR이면 secret 자체가 필요 없어 deployment에서 제거 가능
- [ ] **ArgoCD webhook 연결** - 각 코드 repo의 GitHub webhook을 `https://argocd.movingzero.org/api/webhook`으로 추가하면 폴링 3분을 기다리지 않고 즉시 sync 트리거
- [ ] **PR-level CI 분리** - 지금 워크플로우는 main push에서만 도는데 PR에서 빌드 검증만 따로 도는 워크플로우를 추가하면 머지 전 안전망이 생김
- [ ] **이미지 verify** - cosign 같은 도구로 GHCR 이미지에 서명을 붙이고 ArgoCD에서 unsigned 이미지는 sync 거부하도록 강화
- [ ] **알림** - 배포 성공/실패를 Discord나 Slack에 흘려 보내는 ArgoCD Notifications 설정
- [ ] **Secret 관리** - `secret.yaml`을 평문으로 들고 다니지 말고 Sealed Secrets 혹은 External Secrets Operator로 git에 올릴 수 있는 형태로 전환

### 트러블슈팅 메모

작업하면서 만난 자잘한 함정들도 메모해 둡니다.

- `argocd login`이 `transport is closing`으로 실패하면 거의 항상 `--grpc-web` 누락
- `Invalid username or password` 시 `argocd-initial-admin-secret`의 값이 stale일 가능성. `admin.passwordMtime` 확인
- Kustomize의 `bases:` 키는 deprecated. `resources:`로 마이그레이션
- Helm이 owned한 ConfigMap에 Kustomize patch 시도하지 말 것. 차트의 values 키 활용
