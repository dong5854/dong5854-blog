Deployed는 데이터의 영속성·비용·캐시와 자료구조를 설계하는 Electron 기반 퍼즐 게임이다. 사무실 화면 한쪽에는 배경 음악을 틀어주는 라디오(`OfficeRadio`)가 있는데, 퍼즐 화면에 들어가도 음악이 끊기지 않고 이어져야 하며 사무실로 돌아왔을 때도 재생 상태를 그대로 유지해야 한다.

이 라디오 기능을 구현한 코드를 따라가면서 화면 전환 시 컴포넌트가 유지되는 원리, HTML `<audio>` 요소와 React 화면 상태의 동기화, 그리고 셔플과 재생 목록을 편집·저장·복원하는 흐름에서 헷갈렸던 지점들을 정리했다.

# 숨겨도 음악이 이어지는 이유

`src/renderer/app/Game.tsx`는 퍼즐 화면에 진입했을 때도 사무실 데스크톱(`OfficeDesktop`)을 언마운트하지 않고 바깥 `div`의 `hidden` 속성만 바꾼다. (기존에는 화면 선택 상태 이름이 `tutorial`이었으나, 해시 퍼즐까지 포괄하도록 `activePuzzle`로 이름을 정리했다.)

```tsx
<div hidden={activePuzzle !== false}>
  <OfficeDesktop visible={activePuzzle === false} onStart={(puzzle) => void enterPuzzle(puzzle)} />
</div>
```

`hidden` 속성이 바뀌더라도 React 트리에서 컴포넌트의 위치는 그대로 유지되므로, 내부의 `OfficeRadio`와 `<audio>` 요소도 사라지지 않고 재생을 이어간다.

만약 `hidden` 대신 사무실 화면에서만 `OfficeDesktop`을 조건부 렌더링한다면 어떻게 될까? 퍼즐에 진입하는 순간 컴포넌트가 트리에서 제거되면서 `OfficeRadio`도 언마운트되고, 마운트 effect에 등록된 cleanup이 실행된다.

```tsx
return () => {
  disposed = true
  player.pause()
}
```

마운트 effect 내부에서 오디오 요소(`audio.current`)를 가리키는 `player`가 `pause()`를 호출하면서 음악이 멈춰 버린다. 다시 사무실로 돌아왔을 때도 기존 오디오 요소를 이어 쓰는 것이 아니라 새 컴포넌트와 새 오디오 요소가 만들어진다. 화면이 바뀌어도 음악이 끊기지 않아야 한다면 컴포넌트를 트리에서 제거하지 않고 숨기는 방식을 써야 한다.

컴포넌트 유지와 저장소를 통한 설정 복원도 구분할 필요가 있다. 만약 조건부 렌더링으로 인해 컴포넌트가 다시 마운트된다면 내부의 React 상태는 초기값(예: 초기 음량 `useState(35)`)부터 다시 시작한다. 현재 구현처럼 `localStorage`에서 기기별 음량(`deviceAudio()`)을 읽어와 복원할 수는 있지만, 이는 새로 마운트된 컴포넌트가 저장소에서 값을 다시 불러오는 것일 뿐 기존 오디오 인스턴스와 재생 흐름이 그대로 유지되는 것과는 다르다.

# 화면의 버튼과 실제 오디오 요소

`src/renderer/office/OfficeRadio.tsx`의 `<audio>` 태그에는 `controls` 속성이 없다. 브라우저의 기본 플레이어 UI를 숨기고, 별도로 만든 커스텀 버튼과 슬라이더가 `ref={audio}`(`audio.current`)를 통해 실제 오디오 요소를 조작하는 구조다.

```tsx
<audio
  ref={audio}
  preload="metadata"
  onPlay={() => setPlaying(true)}
  onPause={() => setPlaying(false)}
  onTimeUpdate={() => setElapsed(audio.current!.currentTime)}
/>
```

화면의 재생 버튼을 누르면 `play()` 함수가 호출되고, 내부에서 오디오 요소의 `.play()`를 실행한다.

```tsx
function play() {
  setError('')
  void audio.current!.play().catch((reason) => {
    if (reason.name !== 'AbortError') setError('음악을 재생하지 못했어요. 다시 시도해 주세요.')
  })
}
```

여기서 눈에 띄는 점은 `play()` 함수 안에서 직접 `setPlaying(true)`를 호출하지 않는다는 것이다. 만약 재생 요청이 실패했는데 버튼 클릭 핸들러에서 무조건 화면 상태를 '재생 중'으로 바꿔 버리면 실제 오디오와 UI 표시가 어긋난다.

대신 `audio.current.play()`로 재생을 요청하고, 오디오 요소의 일시정지 상태가 해제되어 `onPlay` 이벤트가 발생했을 때 `setPlaying(true)`로 화면을 갱신한다. 일시정지 역시 `audio.current.pause()`를 호출한 뒤 오디오에서 발생한 `onPause` 이벤트를 받아 `setPlaying(false)`를 반영한다. 버튼 클릭으로 상태를 미리 추측하지 않고 미디어 요소의 이벤트를 화면 상태의 근거로 삼는 방식이다. 다만 play 이벤트는 paused가 false로 바뀌었음을 알리며, 실제 소리 출력이나 버퍼링 종료까지 보장하지는 않는다. 재생 준비와 중단 상태를 더 세밀하게 표시하려면 playing·waiting·error 이벤트도 함께 다룬다. [play 이벤트 문서](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play_event)

# 일시정지와 정지는 어디에서 갈라지는가

재생 중 일시정지 버튼을 누를 때와 정지 버튼을 누를 때의 차이는 다음 코드에서 갈린다.

```tsx
// 일시정지 분기
audio.current!.pause()

// 정지 버튼의 처리
audio.current!.pause()
audio.current!.currentTime = 0
setElapsed(0)
```

30초까지 재생한 상태에서 일시정지 후 다시 재생하면 멈췄던 30초부터 이어지지만, 정지 후 재생하면 0초부터 시작한다. 이 차이를 만드는 두 줄이 담당하는 대상은 서로 다르다.

| 값                          | 역할                         |
| --------------------------- | ---------------------------- |
| `audio.current.currentTime` | 실제 오디오 재생 위치        |
| `elapsed`                   | React가 화면에 표시하는 시간 |

만약 정지 처리에서 `audio.current!.currentTime = 0`을 빼먹고 `setElapsed(0)`만 남기면 어떻게 될까? 정지 버튼을 누른 직후 화면의 시간은 0초로 표시되지만, 실제 오디오의 위치는 여전히 30초에 머물러 있다. 이후 다시 재생을 누르면 음악은 30초부터 흘러나오고, 뒤이어 발생하는 오디오의 `timeupdate` 이벤트에 의해 화면 시간도 다시 30초로 맞춰진다. 화면 상태(`elapsed`)를 바꿨다고 해서 실제 오디오 요소의 재생 위치까지 바뀌는 것은 아니다.

# 슬라이더 조작과 시간 동기화의 방향

재생 위치를 옮기는 `<input type="range">` 슬라이더의 핸들러는 다음과 같다.

```tsx
onChange={(event) => {
  const next = Number(event.target.value)
  audio.current!.currentTime = next
  setElapsed(next)
}}
```

처음에는 슬라이더를 드래그하는 동안에는 시간이 바뀌지 않고 마우스를 놓아야 해당 위치부터 재생된다고 생각했다. 표준 HTML의 `change` 이벤트는 조작을 마치고 손을 뗐을 때 발생하기 때문이다. 하지만 React의 `onChange`는 브라우저의 `input` 이벤트처럼 드래그하는 도중 값이 바뀔 때마다 실행된다. 따라서 슬라이더를 움직이는 즉시 실제 재생 위치와 화면 표시가 함께 갱신된다.

음악이 자연스럽게 재생될 때와 사용자가 슬라이더를 움직일 때는 데이터의 이동 방향이 반대다.

```tsx
onTimeUpdate={() => setElapsed(audio.current!.currentTime)}
```

- **자연 재생 시**: 오디오가 진행하면서 발생한 위치를 읽어 React 화면(`elapsed`)에 반영한다. (오디오 → 화면)
- **슬라이더 조작 시**: 사용자의 입력값을 실제 오디오 위치(`currentTime`)와 React 화면(`elapsed`) 양쪽에 동시에 반영한다. (사용자 입력 → 오디오·화면)

한편 일시정지 상태에서 슬라이더를 60초로 옮기더라도 핸들러 안에 `play()` 호출이 없으므로 자동으로 재생이 시작되지는 않는다. 화면 표시와 실제 오디오 위치만 60초로 이동한 채 대기하고, 이후 재생 버튼을 누르면 60초부터 재생된다. 위치 이동과 재생 시작이 별개의 동작으로 분리되어 있다.

# 선택한 목록, 편집본, 실제 재생 순서

라디오는 곡 목록을 다룰 때 목적에 따라 세 가지 상태를 구분한다.

| 상태       | 의미                                |
| ---------- | ----------------------------------- |
| `playlist` | 적용된 곡 목록과 사용자가 정한 순서 |
| `order`    | 셔플 여부를 반영한 실제 재생 순서   |
| `draft`    | 적용하기 전 편집 중인 곡 목록       |

이 중 실제 재생 순서인 `order`를 만드는 함수는 `src/renderer/office/radio-state.ts`에 있다.

```typescript
export function playbackOrder(playlist: string[], shuffled: boolean, current?: string) {
  if (!shuffled) return [...playlist]
  const rest = playlist.filter((id) => id !== current)
  for (let i = rest.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1))
    ;[rest[i], rest[j]] = [rest[j], rest[i]]
  }
  return current && playlist.includes(current) ? [current, ...rest] : rest
}
```

예를 들어 `playbackOrder(['A', 'B', 'C'], true, 'B')`를 호출하면 현재 곡 `'B'`를 제외한 `['A', 'C']`만 무작위로 섞은 뒤, 마지막에 `'B'`를 맨 앞에 붙여 반환한다. 첫 곡은 항상 현재 재생 중인 `'B'`가 되고 나머지 곡들의 순서만 섞인다.

이 함수는 순수하게 곡 ID 배열의 순서만 계산할 뿐, 오디오 요소의 `src`나 `currentTime`을 바꾸지 않는다. 덕분에 `'B'`를 30초째 재생하는 도중에 셔플을 켜도 음악이 끊기지 않고 이어서 재생된다. 셔플을 끌 때도 마찬가지로 원래 `playlist`의 복사본을 반환해 재생 순서만 되돌리며, 실제 곡을 바꾸고 오디오 `src`를 교체하는 작업은 별도의 `select()` 함수가 담당한다.

# 셔플 토글과 React 상태 스냅샷

처음 셔플 버튼 핸들러를 봤을 때는 다음 두 줄로 작성되어 있었다.

```tsx
setOrder(playbackOrder(playlist, !shuffled, track))
setShuffled(!shuffled)
```

처음에는 `shuffled` 앞의 `!`가 어색하게 느껴졌다. 하지만 버튼의 `aria-pressed={shuffled}`가 클릭 전의 '현재 상태'를 나타낸다면, 클릭 핸들러가 계산해야 하는 재생 순서는 클릭으로 반전될 '다음 상태'여야 한다. 꺼진 상태(`false`)에서 버튼을 눌렀다면 켜질 상태(`true`)를 기준으로 순서를 섞어야 하기 때문이다.

그렇다면 상태를 먼저 바꾼 뒤 `playbackOrder()`에 `shuffled`를 넘기면 더 읽기 좋지 않을까?

```tsx
// 현재 렌더에서 shuffled가 false라고 가정 (잘못된 예시)
setShuffled(true)
setOrder(playbackOrder(playlist, shuffled, track))
// 같은 핸들러 안의 shuffled는 여전히 false다
```

이렇게 작성하면 의도대로 동작하지 않는다. React의 상태 setter는 현재 실행 중인 함수의 지역 변수 값을 즉시 덮어쓰지 않기 때문이다. 해당 이벤트 핸들러가 끝날 때까지 `shuffled`는 현재 렌더 시점의 스냅샷 값(`false`)을 그대로 가리키고, 변경된 `true`는 다음 렌더에서야 반영된다([State as a Snapshot](https://react.dev/learn/state-as-a-snapshot)).

'클릭 후의 다음 상태'라는 의도가 코드에서 바로 읽히도록 `nextShuffled` 변수를 추출해 개선했다.

```tsx
const nextShuffled = !shuffled
setShuffled(nextShuffled)
setOrder(playbackOrder(playlist, nextShuffled, track))
```

이렇게 하면 두 setter가 동일한 다음 상태 값을 바라본다. 또한 동기적인 클릭 핸들러 안의 두 상태 업데이트는 핸들러 실행이 끝난 뒤 React가 하나로 배칭(batching)해 처리하므로, 중간 상태의 화면이 불필요하게 렌더링되지 않는다([Queueing a Series of State Updates](https://react.dev/learn/queueing-a-series-of-state-updates)).

# 취소 가능한 편집본(draft)과 저장 실패 처리

‘곡 선택’ 모달을 열 때는 현재 재생 목록을 복사해 편집본(`draft`)을 만든다.

```tsx
setDraft([...playlist])
```

`playlist`를 직접 수정하면 모달에서 체크박스를 누르는 즉시 현재 재생 목록에 반영되어 버리고, 편집을 취소했을 때 원래 목록으로 되돌리기도 번거롭다. 별도의 `draft`를 두면 저장 전까지 기존 `playlist`를 안전하게 유지할 수 있고, 취소할 때는 `closeEditor()`에서 `draft`를 `null`로 비우기만 하면 된다.

편집한 목록을 실제로 저장하고 적용하는 `OfficeRadio.tsx`의 `apply()` 함수는 다음과 같다. 여기서 `ids`는 현재 앱에 등록된 전체 곡 ID 배열이다.

```tsx
async function apply() {
  if (!draft?.length || busy) return
  setBusy(true)
  setError('')
  try {
    const reply = await window.deployed.save(
      JSON.stringify({
        version: 1,
        missionId: 'office-radio',
        contractVersion: 1,
        caseSetVersion: 1,
        playlist: draft,
        knownTracks: ids,
      }),
      'office-radio'
    )
    if (!reply.ok) throw new Error(reply.error)
    setPlaylist(draft)
    setKnown(ids)
    setOrder(playbackOrder(draft, shuffled, track))
    setNotice('재생 목록과 순서를 저장했습니다.')
    closeEditor()
  } catch (reason) {
    setError(`목록을 저장하지 못했어요. 선택은 유지됩니다. ${String(reason)}`)
  } finally {
    setBusy(false)
  }
}
```

파일 저장 요청(`window.deployed.save`)이 실패하면 `throw`가 발생해 아래쪽의 `setPlaylist`, `setOrder`, `closeEditor()`는 실행되지 않는다. 덕분에 기존에 적용되어 있던 `playlist`는 그대로 유지되고, 사용자가 고른 편집본(`draft`)도 닫히지 않은 채 오류 메시지만 표시된다. 이후 `finally`에서 `busy` 상태가 풀려 그대로 다시 저장을 시도할 수 있다.

또한 파일에 저장하는 목록은 셔플된 `order`가 아니라 사용자가 선택한 `draft`다. 저장이 성공한 뒤에야 새 목록(`draft`)과 현재 셔플 상태(`shuffled`)를 조합해 실제 재생 순서(`order`)를 다시 계산한다.

# JSON 파일의 저장 위치와 영속성 범위

화면에서 호출한 `window.deployed.save()`는 preload의 IPC를 거쳐 Electron 메인 프로세스로 JSON 문자열을 전달한다. 저장되는 JSON 구조는 다음과 같다.

```json
{
  "version": 1,
  "missionId": "office-radio",
  "contractVersion": 1,
  "caseSetVersion": 1,
  "playlist": ["Ledge_of_the_Citadel", "Perfected_Logic"],
  "knownTracks": ["Ledge_of_the_Citadel", "Perfected_Logic", "The_AM_Migration"]
}
```

- `playlist`: 사용자가 선택한 곡 ID와 순서
- `knownTracks`: 저장 시점에 앱에 존재하던 전체 곡 ID 목록 (이후 업데이트로 새 곡이 추가되었을 때 곡 선택 화면에서 새 곡임을 표시하는 데 사용한다)
- 버전 및 미션 식별 필드: 메인 프로세스의 저장 형식 검증에 사용

메인 프로세스(`src/main/index.cjs`)는 저장 폴더 경로를 다음과 같이 계산한다.

```javascript
path.join(app.getPath('userData'), 'saves')
```

`app.getPath('userData')`는 운영체제별 앱 데이터 기본 위치에 `package.json`의 앱 이름(`deployed`)을 붙인 경로를 반환한다([Electron app.getPath 문서](https://www.electronjs.org/docs/latest/api/app#appgetpathname)). macOS 환경에서는 다음 경로에 파일이 생성된다.

```text
~/Library/Application Support/deployed/saves/office-radio.json
```

파일을 실제로 쓰는 `src/main/save-store.cjs`는 쓰기 도중 파일이 깨지는 것을 방지하기 위해 새 내용을 `.tmp` 파일에 먼저 기록한 뒤 본 파일로 교체하며, 직전 정상 파일은 `.bak`으로 백업해 둔다.

라디오의 모든 상태가 이 JSON 파일 하나에 들어가는 것은 아니다. 데이터의 성격에 따라 저장 위치가 나뉘어 있다.

- **`office-radio.json`**: 사용자가 구성한 재생 목록(`playlist`)과 확인한 곡 목록(`knownTracks`)
- **`localStorage` (`office-radio-audio`)**: 기기별 음량과 음소거 설정
- **메모리 상태**: 현재 재생 중인 곡, 재생 위치(`elapsed`), 셔플 여부(`shuffled`)

# 저장된 곡이 사라졌거나 중복되어 있을 때의 복원

앱을 다시 실행하면 파일에 저장된 목록을 현재 앱에서 사용 가능한 곡 목록(`available`)과 대조해 복원한다. `radio-state.ts`의 `restorePlaylist()` 함수가 이 역할을 맡는다.

```typescript
export function restorePlaylist(saved: string[] | undefined, available: string[]) {
  const playlist =
    saved?.filter((id, index) => available.includes(id) && saved.indexOf(id) === index) ?? available
  return { playlist: playlist.length ? playlist : available, recovered: playlist.length === 0 }
}
```

이 짧은 코드에는 두 단계의 방어 로직이 들어 있다.

1. **`?.`와 `??`를 통한 초기값 처리**: 저장된 파일이 없어 `saved`가 `undefined`이면 옵셔널 체이닝(`?.`)에 의해 `filter()`를 건너뛰고 `undefined`가 되며, null 병합 연산자(`??`)가 오른쪽의 전체 목록(`available`)을 선택한다.
2. **유효성·중복 제거와 빈 배열 복원**: `available.includes(id)`로 삭제된 곡을 걸러내고, `saved.indexOf(id) === index`로 첫 등장만 남겨 중복을 제거한다. 만약 저장된 곡들이 모두 삭제되어 `filter()` 결과가 빈 배열(`[]`)이 되었다면, 빈 배열은 `null`이나 `undefined`가 아니므로 `??`를 그대로 통과한다. 대신 다음 줄의 `playlist.length ? playlist : available`에서 전체 목록으로 대체되면서 `recovered` 플래그가 `true`가 된다.

사용 가능한 곡(`available`)이 `['A', 'B', 'C']`일 때 입력값에 따른 복원 결과를 비교하면 다음과 같다.

| 저장된 목록 (`saved`)  | `filter` 및 `??` 통과 후 | 최종 `playlist`   | `recovered` |
| ---------------------- | ------------------------ | ----------------- | ----------- |
| `['A', 'B', 'B', 'X']` | `['A', 'B']`             | `['A', 'B']`      | `false`     |
| `['X']`                | `[]`                     | `['A', 'B', 'C']` | `true`      |
| `undefined`            | `['A', 'B', 'C']`        | `['A', 'B', 'C']` | `false`     |

똑같이 기본 목록(`['A', 'B', 'C']`)으로 시작하더라도 처음부터 저장 파일이 없었던 경우(`recovered: false`)와 기존 저장 곡들을 하나도 쓸 수 없게 된 경우(`recovered: true`)를 구분한다. `recovered`가 `true`일 때만 화면에 *"저장된 곡을 찾을 수 없어 전체 곡으로 복원했습니다"*라는 안내를 띄운다.

# 정리: 조작별 오디오와 React 상태 비교

라디오의 재생과 목록 관리를 따라가 보면 사용자의 조작마다 실제 오디오 요소와 React 상태가 각자 맡은 역할을 나누어 처리한다는 점이 명확해진다.

| 조작         | 실제 오디오 요소 (`audio.current`)             | React 상태 및 목록                                |
| ------------ | ---------------------------------------------- | ------------------------------------------------- |
| 일시정지     | `pause()`로 멈추고 현재 위치 유지              | `onPause` 이벤트로 `playing = false`              |
| 정지         | 멈춘 뒤 `currentTime = 0`으로 초기화           | `elapsed`도 `0`으로 초기화                        |
| 시간 이동    | 지정한 위치로 `currentTime` 변경 (재생은 별도) | `elapsed`를 입력값으로 변경                       |
| 셔플 전환    | 현재 곡과 재생 위치 유지                       | `nextShuffled`를 기준으로 `shuffled`·`order` 변경 |
| 곡 목록 편집 | 적용 전까지 기존 목록으로 동작                 | 복사본인 `draft`에서 편집                         |
| 저장 실패    | 기존 목록과 재생 상태 유지                     | `draft` 유지, 오류 표시, `busy` 해제              |
| 저장 성공    | 현재 재생 중인 곡을 즉시 끊지 않음             | 새 `playlist` 적용, `order` 재계산, 편집 종료     |

- **DOM 미디어 상태와 UI 상태의 분리**: 재생 여부(`playing`)와 재생 시간(`elapsed`)은 React 상태이지만, 실제 소리를 내고 시간을 전진시키는 주체는 `<audio>` 요소다. 따라서 상태 변경의 출발점이 오디오 이벤트인지 사용자 입력인지 구분해야 어긋남이 생기지 않는다.
- **상태의 목적별 분리**: 원본 목록(`playlist`), 실제 재생 순서(`order`), 편집 중인 임시 목록(`draft`)을 분리해 두었기 때문에 음악을 끊지 않고 셔플을 토글하거나 저장 실패 시에도 안전하게 편집 상태를 유지할 수 있다.
