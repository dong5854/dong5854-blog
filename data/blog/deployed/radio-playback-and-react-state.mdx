# 화면 전환에서 시작한 라디오 문답

Deployed의 사무실에는 별도의 버튼과 슬라이더로 조작하는 라디오가 있다. 퍼즐에 들어가도 음악은 이어지고, 사무실로 돌아오면 재생 상태를 유지해야 한다. 이번에는 manware-ai-learning-toolkit으로 화면 전환부터 재생 위치의 동기화, 셔플과 재생 목록 저장까지 한 흐름으로 문답을 진행했다.

처음에는 화면에서 라디오를 숨기는 것과 React 컴포넌트를 제거하는 것의 차이를 확인했다. 이후 실제 음악을 재생하는 HTML 요소, 재생·일시정지 이벤트, 화면에 표시하는 시간과 실제 재생 위치의 차이로 질문을 넓혔다. 첫 초안은 여기서 마무리했지만, 더 큰 기능 단위로 묶기 위해 셔플 전환과 재생 목록의 편집·저장·복원까지 추가로 문답했다.

이 글의 코드는 2026년 10월 16~17일 작업 트리에서 확인한 구현을 기준으로 한다. 앞선 문답 이후 라디오에는 저장된 재생 목록과 기기별 음량 복원이 추가되었다. 과거 코드로 확인한 가정과 현재 구현의 차이는 해당 부분에서 구분한다. 학습 중 가정한 변경은 실제 적용한 기능이 아니다. 셔플 처리의 다음 상태를 명시하는 작은 가독성 개선은 문답 중 요청해 적용했다.

# 숨겨도 음악이 이어지는 이유

`src/renderer/app/Game.tsx`는 퍼즐 화면에서도 사무실 데스크톱을 렌더링한 채 바깥 요소를 숨긴다. 줄바꿈만 정리한 실제 코드다.

```tsx
<div hidden={activePuzzle !== false}>
  <OfficeDesktop visible={activePuzzle === false} onStart={(puzzle) => void enterPuzzle(puzzle)} />
</div>
```

`hidden`이 바뀌어도 같은 위치의 컴포넌트와 그 안의 오디오 요소는 유지된다. 문답에서는 컴포넌트가 제거되지 않고 숨겨지기 때문에 상태가 이어진다고 설명했다.

반대로 사무실에서만 `OfficeDesktop`을 조건부 렌더링한다면 어떨까? 이것은 차이를 확인하기 위해 가정한 변경이었다. 퍼즐 진입 시 컴포넌트가 제거되면 그 안의 `OfficeRadio`도 언마운트된다. 현재 라디오의 마운트 effect에는 다음 cleanup이 있다.

```tsx
return () => {
  disposed = true
  player.pause()
}
```

cleanup이 실행되면서 음악이 일시정지한다. 사무실로 돌아왔을 때도 기존 오디오 요소를 그대로 이어 쓰는 것이 아니라 새 컴포넌트가 만들어진다. 그래서 음악을 유지해야 한다면 제거하면 안 된다고 답했다. 이 가정한 조건부 렌더링은 적용하지 않았다.

당시 음량 질문은 이전 코드의 `useState(35)`를 기준으로 했다. 컴포넌트를 다시 만들면 그 초기값부터 시작한다고 답했지만, 현재 구현에는 `deviceAudio()`로 로컬 저장 음량을 복원하는 코드가 있다. 지금도 재마운트하면 반드시 35가 된다고 일반화할 수는 없다. 컴포넌트 유지와 저장소를 통한 값 복원은 구분해야 한다.

화면 선택 상태의 이름도 문답 중 바꿨다. 기존 `tutorial`은 해시 퍼즐까지 선택하는 상태를 표현하기에 좁다고 지적했고, 요청에 따라 `activePuzzle`과 `setActivePuzzle`로 변경했다.

# 화면의 버튼과 실제 오디오 요소

`src/renderer/office/OfficeRadio.tsx`의 `<audio>`에는 `controls` 속성이 없다. 따라서 브라우저의 기본 플레이어 UI는 표시하지 않고, 별도로 만든 재생 버튼과 슬라이더로 조작한다.

처음에는 오디오가 실제로 화면에 보이는 컴포넌트인지 물었다. 설명을 통해 화면에 표시하는 조작부와 실제 재생을 담당하는 HTML 요소를 구분했다. `ref={audio}`는 그 요소를 `audio.current`로 조작할 수 있도록 연결한다. 질문에 필요한 실제 속성만 발췌하면 다음과 같다.

```tsx
<audio
  ref={audio}
  preload="metadata"
  onPlay={() => setPlaying(true)}
  onPause={() => setPlaying(false)}
  onTimeUpdate={() => setElapsed(audio.current!.currentTime)}
/>
```

재생 버튼은 프로젝트에서 만든 `play()`를 호출하고, 그 함수가 오디오 요소의 `.play()`를 호출한다. 아래는 현재 함수 전체다.

```tsx
function play() {
  setError('')
  void audio.current!.play().catch((reason) => {
    if (reason.name !== 'AbortError') setError('음악을 재생하지 못했어요. 다시 시도해 주세요.')
  })
}
```

실패했는데 재생 중으로 표시하면 안 된다고 답했다. 실제 코드도 이 함수 안에서 무조건 `setPlaying(true)`를 호출하지 않고 오디오의 이벤트를 통해 화면 상태를 바꾼다. `onPlay`는 일시정지 상태가 해제되는 이벤트이며, 버퍼 준비나 실제 소리 출력까지 모두 보장한다는 뜻은 아니다. 여기서는 호출, 이벤트, 화면 상태 갱신이 연결되는 경로를 확인했다.

일시정지 버튼에 대해서는 `audio.current!.pause()`가 호출되고, `pause` 이벤트를 받아 `setPlaying(false)`가 실행된다고 설명했다. 버튼 클릭만으로 상태를 추측하는 대신 오디오 요소에서 발생한 이벤트를 화면에 반영하는 구조다.

# 일시정지와 정지는 어디에서 갈라지는가

현재 버튼의 핸들러에서 재생 중 일시정지 분기와 정지 처리를 발췌했다.

```tsx
// 일시정지 분기
audio.current!.pause()

// 정지 버튼의 처리
audio.current!.pause()
audio.current!.currentTime = 0
setElapsed(0)
```

30초까지 재생했다면 일시정지 후 재생은 멈춘 곳에서 이어진다. 정지 후 재생은 0초부터 시작한다. 이 차이를 만드는 줄로 `currentTime = 0`과 `setElapsed(0)`을 짚었다. 두 줄이 담당하는 대상은 다르다.

| 값                          | 역할                         |
| --------------------------- | ---------------------------- |
| `audio.current.currentTime` | 실제 오디오 재생 위치        |
| `elapsed`                   | React가 화면에 표시하는 시간 |

문답에서는 정지 처리에서 `currentTime = 0`만 지우고 `setElapsed(0)`은 남겼다고 가정했다. 이때 화면은 처음 위치를 표시하지만 음악은 멈췄던 곳에서 이어져 불일치가 생긴다고 답했다. 실제 코드에서는 그 줄을 삭제하지 않았다.

다만 화면이 계속 0초에 고정되는 것은 아니다. 이후 오디오의 `timeupdate` 이벤트가 오면 실제 위치로 다시 맞춰진다. 화면 상태만 바꾸었다고 실제 오디오의 위치까지 바뀌는 것은 아니라는 점이 이 가정의 핵심이었다.

# 슬라이더를 놓아야 시간이 바뀌는가

현재 재생 위치 슬라이더의 핸들러는 다음과 같다. `<input type="range">`의 실제 코드에서 발췌했다.

```tsx
onChange={event => {
  const next = Number(event.target.value);
  audio.current!.currentTime = next;
  setElapsed(next);
}}
```

처음에는 드래그하는 동안 화면에 적용되지 않고 슬라이더를 놓아야 해당 위치부터 재생된다고 생각했다. 하지만 React의 범위 입력 `onChange`는 드래그 중 값이 바뀔 때도 실행된다. 이 핸들러는 놓는 시점을 기다리는 처리가 아니다. 값이 바뀔 때 실제 재생 위치와 화면 표시를 함께 갱신한다.

자연스럽게 재생될 때의 연결 방향은 반대다.

```tsx
onTimeUpdate={() => setElapsed(audio.current!.currentTime)}
```

오디오가 진행하면 그 위치를 읽어 React 화면에 반영한다. 사용자가 슬라이더를 움직일 때는 사용자 입력을 오디오 위치와 화면 양쪽에 반영한다. 같은 시간 표시를 다루지만 변경의 출발점이 다르다.

시간 이동의 마지막 질문은 일시정지 상태에서 슬라이더를 60초로 옮기는 경우였다. 이 핸들러에는 `play()`가 없으므로 자동 재생되지 않고 화면은 60초를 표시한다고 답했다. 실제 위치도 60초로 바뀌며, 이후 재생 버튼을 누르면 그 위치에서 시작한다. 위치 이동과 재생 시작을 별개의 동작으로 구분한 답변이었다.

# 선택한 목록과 재생 순서는 같은 상태가 아니다

셔플 문답에서는 먼저 라디오가 가진 세 가지 목록을 구분했다.

| 상태       | 의미                                |
| ---------- | ----------------------------------- |
| `playlist` | 적용된 곡 목록과 사용자가 정한 순서 |
| `order`    | 셔플 여부를 반영한 실제 재생 순서   |
| `draft`    | 적용하기 전 편집 중인 곡 목록       |

이 중 `order`를 만드는 함수는 `src/renderer/office/radio-state.ts`에 있다. 실제 코드다.

```typescript
export function playbackOrder(playlist: string[], shuffled: boolean, current?: string) {
  if (!shuffled) return [...playlist]
  const rest = playlist.filter((id) => id !== current)
  for (let i = rest.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1))
    ;[rest[i], rest[j]] = [rest[j], rest[i]]
  }
  return current && playlist.includes(current) ? [current, ...rest] : rest
}
```

질문에서는 실제 곡 제목 대신 `A`, `B`, `C`라는 설명용 ID를 사용했다. `playbackOrder(['A', 'B', 'C'], true, 'B')`를 호출하면 `B`를 제외한 `A`, `C`만 섞고 마지막에 현재 곡 `B`를 맨 앞에 붙인다. 첫 곡은 `B`이고 나머지 두 곡은 무작위 순서라고 답했다.

이 함수는 곡 ID의 순서를 계산한다. 오디오 요소의 `src`나 `currentTime`을 바꾸는 함수가 아니다. 따라서 B를 30초까지 재생하는 중 셔플을 켜도 B는 재생을 이어간다. 문답에서는 현재 곡을 유지한 채 나머지를 섞는다고 설명했고, 재생 위치를 바꾸지 않는다는 점을 함께 확인했다.

셔플을 끄면 현재 곡을 맨 앞으로 옮기는 분기를 쓰지 않고 원래 `playlist`의 복사본을 반환한다. 이때도 현재 재생 곡을 직접 바꾸지는 않는다. 곡을 실제로 교체하는 `select()`는 별도로 `pause()`, `src` 변경과 필요한 경우의 `play()`를 수행한다.

# 왜 현재 상태 앞에 느낌표를 붙이는가

처음 확인한 셔플 버튼은 다음 두 줄이었다. 이 코드는 문답 도중 가독성 개선 전의 구현이다.

```tsx
setOrder(playbackOrder(playlist, !shuffled, track))
setShuffled(!shuffled)
```

여기서 `shuffled` 앞의 `!`가 납득되지 않았다. 버튼이 켜져 있으면 `true`, 꺼져 있으면 `false`여야 하는데 왜 반대로 전달하는지 물었다. 그 표현이 맞지 않는 것은 아니었다. 버튼의 `aria-pressed={shuffled}`는 현재 상태를 표시한다. 클릭 핸들러에서는 그 상태를 반전시켜 다음 상태를 만들어야 한다.

꺼진 상태에서 클릭했다면 재생 순서도 켜질 상태인 `true`로 계산해야 한다. 켜진 상태에서 다시 클릭했다면 `false`로 계산해야 한다. 후속 답변에서는 `playbackOrder()`가 받는 값이 현재 상태가 아니라 클릭 후의 상태라서 반전이 필요하다고 설명했다.

그다음에는 상태부터 바꾼 뒤 `playbackOrder()`를 호출하면 더 읽기 좋지 않겠느냐고 물었다. 성능 때문인지도 확인했다. 여기에는 React 상태 갱신의 시점이 관련되어 있었다. 다음 코드는 잘못된 순서 계산을 설명하기 위한 가정이며 적용하지 않았다.

```tsx
// 이 렌더에서 shuffled가 false라고 가정
setShuffled(true)
setOrder(playbackOrder(playlist, shuffled, track))
// 같은 핸들러의 shuffled는 여전히 false
```

상태 setter는 현재 실행 중인 함수의 변수를 즉시 대입해 바꾸지 않는다. 해당 핸들러는 그 렌더의 상태 값을 계속 참조하고, 새 값은 다음 렌더에서 받는다. 이 설명은 [React의 상태 스냅샷 문서](https://react.dev/learn/state-as-a-snapshot)로 확인했다.

다음 상태라는 의도가 드러나도록 변경을 요청했고, 실제 버튼 코드를 아래처럼 바꿨다.

```tsx
const nextShuffled = !shuffled
setShuffled(nextShuffled)
setOrder(playbackOrder(playlist, nextShuffled, track))
```

두 setter가 동일한 다음 값을 사용한다. 이 동기적인 클릭 핸들러에서는 코드가 끝난 뒤 React가 상태 변경을 묶어서 처리하고, 컴포넌트를 다시 실행해 새 JSX를 계산한 다음 필요한 DOM 변경을 반영한다. setter 사이에 중간 화면을 따로 표시하기 위한 코드는 아니다. [React의 상태 업데이트 배칭 설명](https://react.dev/learn/queueing-a-series-of-state-updates)을 참고했다.

다음 상태의 의미는 후속 답변으로 확인했다. setter 직후의 상태 값과 렌더·DOM 반영 단계는 AI의 설명으로 배웠으며, 별도 예제로 직접 실행 순서를 예측하는 문답까지 진행한 것은 아니다.

# 취소 가능한 편집본을 만들고 저장 성공 뒤 적용하기

‘곡 선택’을 열 때는 다음 코드로 현재 목록을 복사한다.

```tsx
setDraft([...playlist])
```

`playlist`를 직접 수정하면 편집 중에 바로 적용되기 때문에 별도의 `draft`가 필요하다고 답했다. 편집 결과를 적용하기 전까지 기존 목록을 유지하면 취소할 때 되돌릴 목록을 별도로 재구성할 필요가 없다. 현재 `closeEditor()`는 편집본을 `null`로 만들고 검색어를 비운다.

`OfficeRadio.tsx`의 실제 저장 함수는 다음과 같다. 저장 payload의 버전과 미션 식별 필드도 실제 코드 그대로 포함했다.

```tsx
async function apply() {
  if (!draft?.length || busy) return
  setBusy(true)
  setError('')
  try {
    const reply = await window.deployed.save(
      JSON.stringify({
        version: 1,
        missionId: 'office-radio',
        contractVersion: 1,
        caseSetVersion: 1,
        playlist: draft,
        knownTracks: ids,
      }),
      'office-radio'
    )
    if (!reply.ok) throw new Error(reply.error)
    setPlaylist(draft)
    setKnown(ids)
    setOrder(playbackOrder(draft, shuffled, track))
    setNotice('재생 목록과 순서를 저장했습니다.')
    closeEditor()
  } catch (reason) {
    setError(`목록을 저장하지 못했어요. 선택은 유지됩니다. ${String(reason)}`)
  } finally {
    setBusy(false)
  }
}
```

저장 실패 응답이 오면 `throw`하므로 그 뒤의 목록 갱신과 편집 종료는 실행되지 않는다고 답했다. 따라서 적용된 `playlist`와 편집한 `draft`를 유지한다. 다만 모든 setter가 멈추는 것은 아니다. `catch`에서는 오류 메시지를 설정하고 `finally`에서는 `busy`를 풀어 재시도할 수 있게 한다.

여기서 파일에 넣는 목록은 편집한 `draft`다. 셔플로 계산한 `order` 자체를 저장하는 형태는 아니다. 저장 성공 후 그 목록과 현재 셔플 상태로 `order`를 다시 만든다. 편집한 목록, 저장할 목록, 일시적인 재생 순서가 서로 다른 이유를 현재 코드에서 볼 수 있다.

# JSON 파일은 어디에 저장하는가

저장 흐름을 읽다가 형식과 경로도 물었다. 화면에서 호출하는 `window.deployed.save()`는 JSON 문자열을 preload의 IPC를 통해 메인 프로세스에 전달한다. 메인 프로세스의 저장소가 내용을 검증하고 파일을 쓴다.

다음은 실제 저장 payload와 같은 구조의 설명용 JSON이다. 곡 목록은 짧게 구성한 예시이며 실제 저장 파일 내용을 인용한 것은 아니다.

```json
{
  "version": 1,
  "missionId": "office-radio",
  "contractVersion": 1,
  "caseSetVersion": 1,
  "playlist": ["Ledge_of_the_Citadel", "Perfected_Logic"],
  "knownTracks": ["Ledge_of_the_Citadel", "Perfected_Logic", "The_AM_Migration"]
}
```

`playlist`는 선택한 곡 ID와 순서이고, `knownTracks`는 저장 당시 앱에 있던 전체 곡 ID다. 현재 앱의 곡이 `knownTracks`에 없으면 곡 선택 화면에서 새 곡으로 표시한다. 버전과 미션 식별 필드는 메인 프로세스의 저장 형식 검증에 사용한다.

`src/main/index.cjs`의 저장 폴더 계산 부분은 다음과 같다.

```javascript
path.join(app.getPath('userData'), 'saves')
```

`userData`가 시스템에서 지정하는 경로인지 다시 물었다. 정확히는 운영체제의 기본 앱 데이터 위치를 바탕으로 Electron이 앱 이름을 붙여 정하는 기본 경로다. `getPath()`는 그 경로를 조회한다. 이 프로젝트는 기본 경로를 사용하며, 개발자가 `app.setPath()`로 바꾸는 방식도 가능하다는 설명을 들었다. [Electron의 경로 API 문서](https://www.electronjs.org/docs/latest/api/app#appgetpathname)에서 기본값과 변경 API를 확인했다.

현재 macOS 환경에서는 `package.json`의 앱 이름이 `deployed`이므로 라디오 파일은 다음 위치다. 코드뿐 아니라 이 개발 환경에서 해당 파일과 백업 파일이 존재하는 것도 확인했다. 저장 파일 내용 자체를 열어 문답의 예시 데이터로 사용한 것은 아니다.

```text
~/Library/Application Support/deployed/saves/office-radio.json
```

프로젝트가 직접 정한 부분은 `saves`라는 하위 폴더와 미션 ID를 사용한 파일명이다. 사용자의 홈 디렉터리를 포함한 전체 절대경로를 소스에 고정한 것은 아니다.

`src/main/save-store.cjs`는 새 내용을 `.tmp`에 쓴 뒤 본 파일로 교체한다. 이전 파일이 있으면 검증한 기존 내용을 `.bak`으로 보관한다. 이 저장 경로와 파일 처리 방식은 AI가 소스를 읽어 설명한 범위이며, 이번 문답에서 쓰기 도중 장애를 재현해 검증한 결과는 아니다.

저장하는 데이터의 범위도 구분했다. 재생 목록은 이 JSON 파일에 저장하지만 음량·음소거는 `localStorage`의 `office-radio-audio` 키에 별도로 저장한다. 현재 곡, 재생 시간과 셔플 상태는 위 목록 JSON의 필드에 없다. 화면을 잠시 숨겨 재생이 이어지는 것과 앱을 완전히 종료했다가 설정을 복원하는 것은 서로 다른 경로다.

# 저장된 곡이 사라졌거나 중복되어 있다면

앱을 다시 켜면 저장 데이터의 목록을 현재 사용 가능한 곡 ID와 대조한다. `radio-state.ts`의 실제 복원 코드다.

```typescript
export function restorePlaylist(saved: string[] | undefined, available: string[]) {
  const playlist =
    saved?.filter((id, index) => available.includes(id) && saved.indexOf(id) === index) ?? available
  return { playlist: playlist.length ? playlist : available, recovered: playlist.length === 0 }
}
```

먼저 `??`가 저장값이 없으면 기본 목록을 쓰는 역할인지 물었다. 정확히는 왼쪽 결과가 `null`이나 `undefined`일 때 오른쪽을 사용한다. `saved`가 `undefined`이면 `?.` 때문에 `filter()`를 실행하지 않고 `undefined`가 되므로 `available`을 사용한다. 반면 `filter()`가 빈 배열을 반환했다면 `??`는 그 빈 배열을 그대로 둔다. 빈 배열을 전체 목록으로 대체하는 것은 다음 `return`의 길이 검사다.

설명용으로 저장된 목록을 `['A', 'B', 'B', 'X']`, 사용 가능한 목록을 `['A', 'B', 'C']`로 가정했다. `A`, `B`가 남고 두 번째 `B`는 첫 인덱스와 현재 인덱스가 다르므로 제외되며, `X`는 사용 가능한 목록에 없어서 제외된다고 설명했다.

다음 질문은 저장 목록이 `['X']`인 경우였다. 필터 결과가 비어 있으므로 전체 `available`을 반환하고 `recovered`가 `true`라고 답했다. 같은 기본 목록을 쓰더라도 저장값이 처음부터 없는 경우와 저장 목록을 전부 사용할 수 없게 된 경우는 표시가 다르다.

| 저장된 목록            | 필터·기본값 처리 뒤의 값 | 최종 목록         | `recovered` |
| ---------------------- | ------------------------ | ----------------- | ----------- |
| `['A', 'B', 'B', 'X']` | `['A', 'B']`             | `['A', 'B']`      | `false`     |
| `['X']`                | `[]`                     | `['A', 'B', 'C']` | `true`      |
| `undefined`            | `['A', 'B', 'C']`        | `['A', 'B', 'C']` | `false`     |

이 표는 `available`이 `['A', 'B', 'C']`인 경우다. 반환된 `recovered`가 참이면 현재 화면은 ‘저장된 곡을 찾을 수 없어 전체 곡으로 복원했습니다’라는 안내를 표시한다. 무조건 저장 파일을 읽었다고 믿는 대신 현재 앱에 존재하는 곡으로 목록을 해석한다.

# 한 기능의 상태를 따라 비교하기

재생과 목록 처리를 함께 보면 사용자 조작마다 바뀌는 대상이 보인다. 다음 표는 문답과 현재 소스에 근거한 비교다. 실제 실행 로그는 아니다.

| 조작         | 실제 오디오                                     | React 상태·목록                               |
| ------------ | ----------------------------------------------- | --------------------------------------------- |
| 일시정지     | `pause()`로 멈추고 위치 유지                    | `pause` 이벤트로 `playing = false`            |
| 정지         | 멈춘 뒤 위치를 0으로 변경                       | `elapsed`도 0으로 변경                        |
| 시간 이동    | 지정한 위치로 변경, 재생 시작은 별도            | `elapsed`를 입력값으로 변경                   |
| 셔플 전환    | 현재 곡과 재생 위치 유지                        | `shuffled`와 `order` 변경                     |
| 곡 목록 편집 | 적용 전까지 기존 목록으로 동작                  | `draft`에서 편집                              |
| 저장 실패    | 적용된 목록 유지                                | 편집본 유지, 오류 표시, `busy` 해제           |
| 저장 성공    | 이 적용 함수에서는 현재 곡을 직접 교체하지 않음 | 새 `playlist` 적용, `order` 재계산, 편집 종료 |

# 이번 문답에서 확인한 범위

화면을 숨기는 것과 컴포넌트를 제거하는 것의 차이, 일시정지 이벤트를 통한 React 상태 갱신, 실제 재생 위치와 표시 시간의 구분, 시간 이동이 자동 재생을 뜻하지 않는다는 점은 답변으로 확인했다. 셔플에서 현재 곡을 유지하는 방식, 클릭 후 상태를 사용해야 하는 이유, 편집본을 분리하는 이유, 저장 실패 후의 상태, 복원 시 중복·삭제된 곡을 걸러내는 조건도 설명했다. 특히 실제 오디오와 화면 표시, 적용 목록과 편집본처럼 서로 다른 상태를 구분하는 답변이 분명했다.

슬라이더 `onChange`의 발생 시점과 자연 재생 중 `timeupdate`의 방향은 설명으로 교정했다. React 상태 스냅샷과 배칭도 설명을 들은 범위다. 다음 상태를 명시한 셔플 코드로 ‘클릭 핸들러 안의 값’과 ‘다음 렌더에서 받는 값’을 따로 적어보면 좋은 복습이 된다. 오디오 조작은 일시정지 상태에서 60초로 이동했을 때의 `currentTime`, `elapsed`, `playing`을 적어보는 식으로 확인할 수 있다.

이 글은 현재 소스와 문답을 확인해 작성한 기록이다. 실제 변경은 화면 선택 상태 이름과 셔플의 다음 상태를 명시한 코드에 적용했다. 셔플 가독성 변경 후 타입 검사와 린트는 통과했다. 가정한 조건부 렌더링이나 정지 처리의 변경은 적용하지 않았고, 이번 문답·글 작성 단계에서 Electron 실행 검사는 하지 않았다. 저장 실패와 복원 예시도 새로 장애를 재현한 결과가 아니라 조건식을 따라 판단한 시나리오다.

앞서 이해가 확인된 화면 전환 학습 주석은 삭제했다. 현재 라디오와 목록 유틸리티에는 이번 주제에 해당하는 학습 표시 주석이 남아 있지 않아 추가 삭제는 하지 않았다. 셔플 알고리즘의 확률적 성질이나 재생 중인 곡을 목록에서 제거했을 때의 다음 곡 처리 등은 이번 문답에서 검증하지 않은 후속 주제다.
